# Feature Specification: On-device adaptive outfit engine + 300+ item seed wardrobe

**Feature Branch**: `002-on-device-outfit-engine`

**Created**: 2026-09-29

**Status**: In progress (Sprint 9)

**Input**: "P1 - 300+ real clothing seed dataset + on-device adaptive outfit engine."

## Scope and Intent

DLS already has a working rule-based generator (`OutfitBotService`, `RuleEngine`), optional
LLM enhancement (`AIStylist`), Firestore persistence, and demo seeding (`DemoDataService`).
This feature upgrades the recommendation path to a **local-first, explainable, adaptive**
engine and gives it a realistic development wardrobe, without adding a paid service, a second
clothing model, or a duplicate repository.

Target pipeline:

```
seed data -> local wardrobe -> feature affinity engine -> outfit generator
          -> style match score -> user feedback -> local weight adaptation -> better next fit
```

### In Scope

- A 300+ item development seed wardrobe generated from the **existing** DLS taxonomy.
- A seed generator under `tooling/seed_generator/` producing stable assets + provenance.
- Local-first, network-independent scoring (works offline, no LLM, no paid API).
- Normalised weighted affinity score exposed as a `Style Match` percentage (0-100).
- Variable-length outfit structures (standard, standard+layer, one-piece, one-piece+layer,
  formal, casual/streetwear).
- Weather context from the free Open-Meteo REST API with local caching and a neutral offline
  default; the engine MUST NOT depend on the network.
- Persisted Like/Dislike feedback with local weight adaptation:
  `W_new = W_old + 0.1 x (Feedback - W_old)`, clamped to `[0.0, 1.0]`.
- Dev/demo seeding gated away from production users.
- Tests, and documentation updates (`SCREENS.md`, `PROJECT_HISTORY.md`,
  `AUDIT_TRACKING_PLAN.md`).

### Out of Scope

- Any paid AI/recommendation/image/weather API or hardcoded secret.
- Replacing `ClothingItem`, the Provider graph, Firestore ownership, or the 5-tab shell.
- Real per-item licensed product photography (see Assumptions).
- iOS/macOS device validation (Windows environment limitation).

## Seed Data and Provenance

The seed wardrobe is generated by `tooling/seed_generator/main.dart` and consumes the real
taxonomy from `lib/core/constants/wardrobe_taxonomy.dart` (no duplicated enums).

- Item identity: stable UUIDv5 in a fixed DLS namespace (re-runnable, no duplicates).
- Style labels: **DLS-derived**, restricted to the existing `styleTagOptions` enum.
- Colour group: derived with the existing `deriveColorGroup()`.
- Images: **CC0 only**. Source set = Wikimedia Commons "Europeana Fashion - MoMu - Thesaurus
  drawings" (CC0 1.0, `AttributionRequired = false`), referenced via `Special:FilePath`.
- Provenance record: `assets/seed/dataset_manifest.json`.

**Critical rule**: no dataset may be described as legally suitable unless its licence actually
permits the intended use. No third-party product imagery is bundled or redistributed.

## Affinity Rule Matrix

Scoring is driven by `assets/ml_seed_rules.json`, which currently holds **127 rules** across
**five** dimensions:

| Dimension | Rules | Feeds |
|---|---|---|
| `categoryCompatibility` | 12 | `K` (category/structure) |
| `styleEventAffinity` | 25 | `E` (event) and informs `S` |
| `weatherSuitability` | 72 | `W` (weather) |
| `colorHarmony` | 13 | `C` (colour) |
| `defaultWeights` | 5 | the five scoring weights |

- `styleEventAffinity` is the **full cross-product** of the five `styleTagOptions` against
  the five app occasions (`Work`, `Braai`, `Date`, `Groove`, `Formal event`).
- `weatherSuitability` covers six conditions (`hot`, `warm`, `mild`, `cold`, `freezing`,
  `rain`) across twelve garment classes, each class referencing only real taxonomy
  subcategories.
- `colorHarmony` is a symmetric 3x3 matrix over the colour groups from `deriveColorGroup()`
  plus four patterns (monochromatic, neutral-dominant, complementary, all-accent).
- `defaultWeights` MUST sum to exactly `1.0`.

**Layering is deliberately NOT a separate dimension.** It is integrated in two places:

1. `categoryCompatibility` provides layered structure profiles (`outerwear_layered`,
   `one_piece_layered`, `cold_weather_layered`, `active_layered`).
2. `weatherSuitability` annotates each garment class with `layering`
   (`none`/`single`/`mid`/`outer`/`footwear`/`accessory`), `sleeve`, and `waterproof`, and
   each weather condition with a `layeringNeeded` hint.

These are **priors, not filters**: a low score lowers ranking, it never removes an item.

## Scoring Formula

```
Style Match % = round( 100 * ( w_style*S + w_event*E + w_weather*W + w_color*C + w_category*K ) )
```

where `S`, `E`, `W`, `C`, `K` are each normalised to `[0.0, 1.0]` and the weights come from
`defaultWeights` (sum `1.0`).

Canonical outfit templates validated by the engine: `standard`, `outerwear_layered`,
`one_piece`, `one_piece_layered`.

## User Scenarios

1. **Explainable local fit** - a signed-in user opens the generator, picks an occasion/mood/
   weather, and receives a ranked outfit with a Style Match percentage and a reason, entirely
   offline.
2. **Adaptive learning** - the user likes/dislikes a fit; the contributing affinities update
   locally and future ranking shifts, without touching unrelated rules.
3. **Context sensitivity** - changing event, weather, or style changes candidate scoring and
   the Style Match score.
4. **Development wardrobe** - a developer/demo build on an empty account loads the 300+ seed
   items; a production build never invents a wardrobe.

## Functional Requirements

- **FR-001** The seed dataset MUST contain >= 300 items using only supported DLS categories,
  colours, styles, seasons, genders, and statuses.
- **FR-002** Every seed item MUST have a stable, unique UUID and a resolvable CC0 image
  reference.
- **FR-003** The engine MUST score outfits from normalised components (style, event, weather,
  colour harmony, category compatibility) and return a 0-100 score.
- **FR-004** The engine MUST support variable-length outfit structures.
- **FR-005** The engine MUST run locally without a network call, LLM, or paid API.
- **FR-006** Weather MUST come from Open-Meteo when online, be cached, and fall back to a
  cached or neutral value offline; the engine MUST NOT be blocked by weather failure.
- **FR-007** Feedback MUST persist locally and update only the affinities that contributed to
  the displayed recommendation.
- **FR-008** Seed/ demo data MUST be gated so production users are never auto-seeded.
- **FR-009** All new user-visible text MUST be recoverable and free of raw exception detail.

## Non-Functional Requirements

- **NFR-001** No new paid dependency, key, or secret; no new dependency unless unavoidable.
- **NFR-002** Scoring for 300+ items MUST not block the UI thread for perceptible periods.
- **NFR-003** Offline behaviour MUST be explicit (cached/stale/neutral states distinguished).
- **NFR-004** `flutter analyze` and `flutter test` MUST pass; evidence recorded in
  `AUDIT_TRACKING_PLAN.md`.

## Assumptions

- Images are referenced by remote CC0 URL for this slice; local bundling is a follow-up, so the
  offline-only image requirement is temporarily relaxed (accepted risk, recorded).
- `geolocator` is **not** added; a configured/default location is used, matching the existing
  Johannesburg weather card.

## Success Criteria

1. `assets/seed/wardrobe_seed.json` contains >= 300 validated items with unique ids.
2. `dataset_manifest.json` records source, licence, and transformations truthfully.
3. A recommendation renders with a real computed Style Match percentage offline.
4. Like/Dislike persist and measurably change the stored weights with correct clamping.
5. Production mode performs no seeding.
